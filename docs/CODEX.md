# Codex and Claude host integration

The kernel's claims, checker verdicts, evidence lifetime, review proof, accepted
risk and ship predicate are shared. Host integration supplies instructions,
tool events, task identity and execution access.

## Install the selected hosts

```sh
/path/to/vibeproof/bin/v4 --repo /path/to/project init --hosts both
# Set the actual test_command and confirm this project's facts.
/path/to/vibeproof/bin/v4 --repo /path/to/project install --hosts both --activate-hooks
```

The default is still Claude. Current Claude Code also has a separate SubagentStop
event; activation connects worker stops and supplies SessionStart/SubagentStart
identity for both hosts. Existing settings are changed only with explicit activation. Use --hosts codex for Codex assets, --hosts claude
for Claude assets, or --hosts both. Omitting the option on reinstall preserves
the choice. An explicit --activate-hooks merges framework handlers and preserves
unrelated settings and handlers. Without it, installation supplies templates.
It does not trust hooks or change user-level Codex settings.

Codex loads the project AGENTS.md, .agents/skills/vibeproof-run,
.agents/skills/vibeproof-wave, .agents/skills/vibeproof-sweep and
.agents/skills/vibeproof-maintain. Its custom
agents are v4-task-splitter, v4-worker, v4-reviewer, v4-checker-author and
v4-monitor. Claude retains its existing agents and commands. Codex projections
are generated from their maintained prompt bodies by tools/render_host_assets.py.
Run that script with --write after changing a canonical prompt; without --write
it checks the generated bytes.

Doctrine is generated into the selected hosts' instruction files. Existing
content outside the doctrine markers is preserved. Use ./bin/v4 doctrine --write;
./bin/v4 doctrine --check checks every selected destination.

## Hook trust and coverage

Review and trust the installed definitions in Codex /hooks. A project file
existing is not evidence that it is trusted or running. Codex hooks observe
PreToolUse for apply_patch and Bash, Stop for the parent, and SubagentStop for
v4-worker. SessionStart and SubagentStart supply identity context.

The write handler parses all patch paths, including rename sources and
destinations. Any refused path refuses the entire call. A malformed patch is
refused with a reason. Existing Claude Write/Edit/NotebookEdit inputs continue
to use the same scope and engagement decision.

Bash and patches are separate coverage routes. Interactive write_stdin input,
hosted tools and external browser/connector side effects are not claimed to be
covered by the file hook. Shell guards remain early friction, not a sandbox;
scope also checks the resulting Git diff.

./bin/v4 host status --session SESSION reads that Codex session's recorded hook
events; `--agent AGENT` narrows to that agent, and composes with `--session` and
`--host`. Its observed/checked/stood_down fields describe different facts.
Doctor reports configuration and historical observations; current host trust
is still a host-owned fact. Claude observations cannot establish Codex coverage.

The observed, checked and stood_down lists describe the three guards:
write_block, bash_guard and stop_gate. SessionStart/SubagentStart identity events
are recorded separately as session_context hook events; they are not an
additional guard verdict and do not count as write protection.

## Bind an agent to its task

After opening or receiving a development task, use the identity from the host
context and bind from that task's worktree:

```sh
./bin/v4 --repo /absolute/worktree host bind --task TASK --session SESSION --agent AGENT
```

Use --host claude for Claude identities and --host codex for Codex (the CLI default).
Omit --agent for the parent. The append-only binding must name an open task in
that worktree. Rebinding writes a new event; an ended binding cannot resurrect an
older task. A shell export cannot set the environment of the host that fires hooks.

Both hosts select tasks by their recorded worktree before considering session
marks; tasks without old worktree metadata remain unresolved candidates.
Use one worker task per worktree. Every command must name --repo and --task where
the command takes a task. Use an explicit command working directory and absolute
patch paths when operating in another worktree. Absolute sibling-worktree patches
are accepted only within the same Git common directory. Ambiguous tasks in one
worktree are refused instead of assigned to the newest task.

Both write and stop hooks read parent and child bindings. Ambiguity messages
include the current host and session in the command; --host matters because the
CLI default is codex, including when invoked from Claude.

Workers report back; the orchestrator calls ship. Stop and SubagentStop preserve
the original once-only continuation behavior for a single host stop episode;
a later independent turn may ask again. Read-only questions do not require
opening or binding development tasks.

The maintained run/wave prompts also manage original request intake and current
project documents. Before recording input, the host reads same-repo `coordinate
status` without a goal filter, active task/worktree records and current source,
then compares the original new request with existing inputs/work. Partial overlap
and preserved work reuse the relevant goal; a new goal needs an explicit
reasoned unrelated decision. Unclear relationships or contradictory intent are
preserved for owner judgment before dependent fanout. Do not force all work back
into a queue or enroll unrelated legacy tasks. Related queued work changes by
revision; running work follows the existing stop/reconciliation protocol.
The host then records input text and actual source identities,
assesses partial additions/changes/cancellations and reconciles queued/running
work before fanout. Each managed assignment carries goal/work/revision,
dependency versions and task/worktree coordinates. `check-dispatch` is read-only
and cannot authorize a launch. Commit `coordinate begin-dispatch` before native
spawn and launch once only on its fresh `launch_authorized=true` response. Never
spawn on an idempotent replay. If the claim response or subsequent receipt is
lost, reconcile the dispatching assignment with the actual host; a replacement
requires authoritative release, a new assignment and a new launch claim. Record
the real host observation after spawning. No
message ID or agent ID supplied means missing provenance; an empty parent agent
is valid and must not be replaced with a fabricated name. A recorded stop request needs a separate
actual host stopped observation.
When preparing a future child, leave its worker identity unknown until the
actual dispatched receipt can bind the observed tuple. Do not invent a child ID
or substitute the parent's identity. A known existing worker or parent can
provide its actual tuple at assignment; a known parent with an empty agent ID
is distinct from unknown identity. Unknown or conflicting worker identity holds
independent design review and completion.
The consumer checkout must contain settled dependency artifact commits in its
current HEAD ancestry; assignment, pre-launch checks and completion recheck this.
Revalidate the actual combined source after bringing those commits into the tree.

The orchestrator selects existing project design/specification files and manages
accepted versions; workers update affected scoped coverage. Missing documents
need actual host authorship after checking code/tests/known intent, retaining an
observed-baseline basis where appropriate. Each managed revision needs required
coverage or a source-bound N/A. A distinct reviewer reads the original inputs,
code, tests and document and records a fresh content/source/version-bound review
from the assigned worktree. The receipt does not authenticate identity or prove
all semantic correctness. Accepted target design can remain unimplemented.

After results, the orchestrator checks current versions and task evidence. Git
integration and merged revalidation remain native work. Without actual clean
target completion and artifact ancestry, settlement stays waiting for integration
and dependencies remain held. `coordinate`/`design` do not read conversations,
spawn/stop agents, author project documents or merge. Their executable schemas
own argument details; see [SPEC](SPEC.md#request-evolution-and-project-design-documents)
and [USING](USING.md#the-seven-steps-of-a-task).

For retained disposable acceptance evidence, run
`python3 tools/request_acceptance.py --out <private-evidence-dir>`. The default
mode exercises the public JSON CLI against real Git worktrees and a shared
ledger. `--native-host codex` or `--native-host claude` additionally requests a
real native host session with independent document review; `--timeout` bounds
that transport. Inspect the retained results and transcript separately: direct
CLI scenario success does not establish that a host followed its prompts.
For Codex, `--codex-bin <executable>` selects the native binary and
`--persist-session` retains its transcript for child hooks; the driver forwards
both to `native_host_acceptance.py`. Without these flags it uses Codex on PATH
and an ephemeral session. Both options are refused for Claude.

Retain the native child reference the spawn tool actually returns, whether a
canonical task name or an ID, and use the available wait API's argument schema.
Close a child only when the host exposes that operation. Map the native
reference to the actual injected or raw-hook identity tuple; a returned name,
an assumed UUID or a child's narrative does not establish that its hooks ran.

If an existing review finding names a Python function/method that was renamed,
keep its original claim ID. Offer the normal executable closure with
`review close --rename-commit <commit>` as well as its test, command and
parent-or-mutation proof; repeat the flag for ordered rename steps. The shared
kernel verifies a unique same-file rename in Git with unchanged scope,
signature, decorators and body, then requires the renamed symbol to run. Both
hosts use this path. Uncommitted or mixed rename/body edits need a separate
committed rename before this evidence can be offered; no risk or text-only
substitute is implied.
For a parent-based red control, choose a parent that already includes the
verified rename; an import failure caused solely by the old name is refused.
Mutation proof remains available when the repair preceded the rename.

## Framework location and permissions

The installed launcher and hooks need the framework checkout. Installation writes
the local .v4/home and the shared Git-common-dir/v4/framework-home marker.
The shared marker survives creation of a linked worktree even though .v4/home
is ignored. V4_HOME is an explicit override. A separate clone still needs a
local installation or reachable framework setting.

The ledger remains Git-common-dir/v4/ledger.db, shared by linked worktrees.
The default Codex workspace sandbox protects .git, including the ledger.
Generate a local profile proposal from the actual Git common directory:

```sh
./bin/v4 --repo /absolute/project host permissions
./bin/v4 --repo /absolute/project host permissions --git-operations
```

The first grants the ledger subtree while retaining the .git/.codex/.agents
protections. The second additionally lists the Git index, objects, refs, logs and
worktree state needed for development and isolated acceptance. Review and select
the profile in the host; no command here silently changes active permissions.
Network access is disabled in these profiles. A project needing live services
must declare and configure its actual environment. A local browser suite also
needs permission for loopback connections and local server binding. For an
authorized surface test, use the host's supported session/project controls to
allow the required local targets; keep the default offline profile unchanged.
Browser sandbox/cache permissions and installed browser binaries are host
prerequisites. A denied launch or connection is not surface PASS.

On macOS, a profile can permit the local server while Chromium is still denied
Mach bootstrap access. The orchestrator can request supported one-command
escalation for the same inspected checker/test command. With the host configured
for `approval_policy = "on-request"` and `approvals_reviewer = "auto_review"`,
eligible requests use the host reviewer; this does not grant approval by itself.
The approved command runs outside the ordinary sandbox, while other commands
retain their profile. Keep the failed attempt, actual decision and fresh proof;
an explicit denial is not permission to switch launch methods or disable guards.
In the tested Codex CLI 0.153.4, retaining the session avoids the ephemeral
mode's unavailable guardian transcript warning. This is a host permission flow,
not a promise that Chromium runs inside an unchanged restrictive sandbox.

`tools/native_host_acceptance.py` uses an ephemeral Codex session by default.
For an acceptance scenario whose subagent hooks need the parent transcript,
pass `--persist-session`; the runner records that choice in `run.json` and
otherwise keeps the same reviewed hook and permission arguments. Retain the
failed ephemeral attempt separately. A persistent retry still needs read-back
from the actual task, agent and hook owners before the scenario can pass.

Claude-only installations retain the original protected-path defaults so adding
host support does not silently impose new risk requirements on existing Claude
projects. Selecting Codex additionally protects .codex/**, .agents/** and
hooks/**; selecting both uses that union. For identical control-file protection
in both hosts, explicitly add hooks/** and .claude/settings.json to the project's
protected_paths. The framework's own config already declares those paths.
This compatibility choice does not exempt ordinary files from a task's scope.

Profile selection and legacy sandbox_mode configuration are different Codex
mechanisms; do not assume both compose. The installed config.template.toml is a
starting point for a simple main worktree, while host permissions resolves the
actual shared ledger location. Never replace an isolated accept run with --here
just to avoid Git permissions.

Doctor is read-only; missing ledgers are reported, not initialized by diagnostics.

## Scope of support

The work is developed and validated on macOS. Claude and Codex runtime evidence
must be reported separately. All lenses can be scheduled within host capacity;
the number running simultaneously is not guaranteed. Blind reviewers must start
without worker rationale or inherited task history. Neither a separate model
nor a prompt file proves independent judgment.

No native Windows or Cloud equivalence follows from a macOS test. Runtime/UI
proof still needs a real declared trigger, test command and truth owner.


Host protocol references: [Codex hooks](https://learn.chatgpt.com/docs/hooks) and [Claude Code hooks](https://code.claude.com/docs/en/hooks).


## Maintenance and native scheduling

`/maintain` and `$vibeproof-maintain` share the workflow in
`.claude/commands/maintain.md`; generated Codex assets add native dispatch guidance.
Start roles with explicit repo/run/task inputs and a fresh context. In Claude
headless runs, foreground tasks return a blocking result; background tasks need
an available wait/read-back tool. A returned agent ID or process exit alone is
not completed work. Foreground results may arrive before the parent receives the
host ID; the handoff keeps them pending until that actual receipt is recorded.

The native host owns scheduled tasks. Use its available scheduling tool to
create/update/read the real job and then record that observation through
`maintain schedule`. A local config entry cannot prove a job exists or fired.
Schedule input is checked against the observation producer before writing;
missing or extra fields return `REFUSED` (exit 2) without replacing the previous
observation. `observed_at` is generated by the kernel, not an input field.
Persistent desktop scheduling and Claude session-scoped cron/loop have different
lifetimes; unsupported or inaccessible native scheduling remains explicit.
See [Codex scheduled tasks](https://learn.chatgpt.com/docs/automations?surface=app)
and [Claude scheduling](https://code.claude.com/docs/en/scheduled-tasks) for host
capabilities; verify the actual installed version and job, not just these pages.

Keep disposable development repositories/worktrees outside an enclosing `.git`
directory when the host treats that location as sensitive. Evidence can remain
under the framework’s private Git directory. Do not route around a native
permission rejection with a different writing tool. Use the host’s supported
authorized project/worktree location and keep the rejected observation visible.

Telegram needs a configured destination and secure token file. The separate
macOS launchd receiver processes button callbacks without an LLM; its native
service status and successful Telegram polling are distinct observations. Live
phone delivery/ack is still a separate acceptance step.


A controlled native Codex 0.153.4 probe with explicit exec workdir observed that
Bash-hook payloads carried only `tool_input.command` and the session cwd, while
`pwd` actually ran in a sibling worktree. Both parent and fresh-agent calls had
this mismatch. The hook cannot reconstruct omitted execution coordinates from
that payload; Bash hook counts are not proof of per-worktree pre-write scope
coverage. Keep explicit CLI repo/task coordinates, task-bound post-write checks
and actual native file/patch observations separate. This is an observed host
limitation, not permission to weaken or bypass a guard.
